- `pull_request.py` defines `bind_pull_request_explicit` as a pure alias of `bind_pull_request` with identical signature and body; it adds no behavioral distinction and is not referenced by any caller in the patch, making it dead code that could confuse future maintainers about whether a distinct "explicit" variant is intended.
- The trust-boundary scan in both `acceptance.py` (case 18) and `bundle_evidence.py` uses the literal substring pattern `'"git", "{verb}"'` to detect Git writes. This is a reasonable heuristic but would miss a hypothetical `subprocess.run(("git", "commit"))` (tuple instead of list) or a dynamically constructed argv. A slightly broader pattern (e.g., checking for `"git"` adjacent to the verb in any container literal) would be marginally more robust. This is a minor hardening opportunity, not a correctness gap, since the release layer is the only module that imports `subprocess` for Git operations.
- In `merge_gate.py` `go_merge`, the idempotency short-circuit (`if store.exists(...): existing = store.load_merge_result(...); if existing.merged: return existing`) returns the prior result without re-validating the authorization. This is acceptable because the merge already happened, but a strict reading of "recheck immediately before any write" could argue the authorization should still be validated even on the idempotent path. In practice this is safe (no write occurs) and the authorization was already validated on the first call.
